# ROADMAP · 발전 트랙

이번 실습(일정·출석 보드, localStorage)을 끝낸 뒤 **백엔드 · DB · 프론트 · 앱 · AI · AWS**로 넓혀 가고 싶은 사람을 위한 지도입니다.
튜토리얼이 아니라 **어디를 바꾸면 되는지, 무엇을 먼저 정해야 하는지**만 적습니다. 기술 선택과 깊은 내용은 각 트랙 담당이 ADR과 PR로 직접 채웁니다.

## 1. 트랙 한눈에 보기

| 트랙 | 바뀌는 곳 | 먼저 정해야 할 것 | 첫 Issue |
| --- | --- | --- | --- |
| 백엔드 | `src/domain/storage.ts` 자리를 API 호출로 교체 | API 계약(경로·요청·응답·오류), 인증 여부 | [BE-1 API 계약서](issues/roadmap/be-1-api-contract.md) |
| DB | 서버 뒤의 저장소 | 테이블 구조(일정·출석을 나눌지), 어떤 DB를 쓸지 | [DB-1 ERD와 첫 스키마](issues/roadmap/db-1-erd.md) |
| 프론트 | `src/features/`, 화면 분리·라우팅 | 화면을 나누는 기준, 상태 관리 방식 | [FE-1 일정 상세 페이지](issues/roadmap/fe-1-session-detail.md) |

| AWS | 배포·운영 | 무엇을 어디에 올릴지, 월 비용 상한 | [OPS-1 프론트 정적 배포](issues/roadmap/ops-1-static-deploy.md) |

## 2. 순서와 의존 관계

```text
프론트(FE) ─────────────────────────────── 지금 바로 시작 가능
AI ──(1단계: 브라우저 밖 서버가 필요)──┐
백엔드(BE) ──▶ DB ──▶ AWS(서버 배포)   │
   │                                   │
   └──▶ 앱(APP)  ◀── 같은 API 사용 ─────┘
AWS(프론트 정적 배포) ──────────────────── 지금 바로 시작 가능
```

- **FE-1, OPS-1**은 지금 구조 그대로 시작할 수 있습니다.
- **DB·앱·서버 배포**는 백엔드의 API 계약(BE-1)이 머지된 뒤에 시작합니다.
- **AI**는 API 키를 브라우저에 둘 수 없으므로 서버가 필요합니다(4절 AI 참고).

## 3. 바꾸면 안 되는 약속 (모든 트랙 공통)

## 4. 트랙별 안내

### 백엔드 (BE)
- **출발점**: `storage.ts`의 `readSessions`·`saveSessions`. 지금은 동기 함수라서, 서버 호출로 바꾸면 비동기가 되고 `App.tsx`의 초기 로딩·저장 실패 처리가 달라집니다. 이 영향 범위를 ADR에 적습니다.
- **먼저 정할 것**: 경로와 메서드, 응답 형식(성공·오류를 한 모양으로 감쌀지), 오류 코드 목록, 인증 여부, 프론트 개발 서버 주소(`http://localhost:5173`) CORS 허용.
- **산출물**: `docs/API.md`(계약서) → 서버 코드는 저장소를 나눌지(ADR) 정한 뒤.
- **ADR 제목 예**: `0003-backend-framework.md`, `0004-api-response-format.md`

### DB
- **출발점**: `Session.attendees`가 이름 배열입니다. 관계형 DB라면 일정 테이블과 출석 테이블을 나누는 게 보통이고, 문서형 DB라면 지금 모양을 그대로 둘 수도 있습니다. 이 선택이 첫 ADR입니다.
- **먼저 정할 것**: DB 종류, 멤버를 테이블로 둘지(지금은 `members.ts` 상수), 삭제 시 출석 기록 처리, 로컬 개발용 DB 실행 방법.
- **산출물**: `docs/ERD.md`(그림 또는 표), 첫 스키마·마이그레이션.

### 프론트 (FE)
- **출발점**: 지금은 한 화면에 카드 네 개입니다. 일정이 많아지면 목록 → 상세 화면 분리가 필요합니다.
- **먼저 정할 것**: 화면(라우트) 목록과 주소 규칙, 상태를 어디에 둘지(지금처럼 App 상태 / 별도 상태 관리 도구), 새 패키지를 들일지.
- **지킬 것**: 새 화면도 `src/features/<기능>/` 폴더 규칙과 클래스 이름 규칙을 따릅니다.

### 앱 (APP)
- **출발점**: 같은 데이터를 쓰는 두 번째 클라이언트입니다. 서버가 없으면 웹과 데이터를 공유할 수 없으므로 BE-1이 먼저입니다.
- **먼저 정할 것**: 방식(웹을 설치형으로 만드는 PWA / 크로스플랫폼 앱 / 네이티브), 웹과 공유할 코드(`domain/types.ts`의 타입, 순수 함수), 앱 전용으로 둘 기능 범위.
- **추천 범위**: 처음에는 “출석 체크만” 되는 화면 하나.

### AI
- **출발점**: 일정의 `title`·`topic`과 출석 데이터. 예: 회차 주제 요약, 다음 스터디 주제 추천, 출석 패턴 알림 문구.
- **먼저 정할 것**: 무엇을 자동화할지(한 가지), 사용할 AI 서비스, 월 비용 상한, 보내는 데이터에 개인정보가 없는지, 결과가 틀렸을 때 화면에서 어떻게 보이게 할지.
- **꼭 지킬 것**: AI 서비스 API 키는 **브라우저 코드에 넣지 않습니다**. Vite에서 `VITE_`로 시작하는 환경변수는 빌드 결과에 들어가 누구나 볼 수 있습니다. 키는 서버에만 둡니다.

### AWS (OPS)
- **출발점**: 지금 앱은 `npm run build` 결과(`dist/`)만 올리면 되는 정적 사이트입니다. 서버가 생기면 서버 실행 환경과 DB가 추가됩니다.
- **먼저 정할 것**: 프론트·서버·DB를 각각 어디에 올릴지, 월 비용 상한과 예산 알림, 접속 키 보관(GitHub Secrets), 배포를 자동으로 할지(main push 시).
- **꼭 지킬 것**: 루트 계정 키를 만들지 않고 실습용 권한만 가진 사용자를 씁니다. 실습이 끝나면 만든 자원을 지웁니다.

## 5. 트랙 시작하는 법

1. 이 문서의 첫 Issue 초안(`docs/issues/roadmap/`)을 GitHub Issue로 만듭니다(✨ 기능 폼에 붙여 넣기). 라벨은 `feat` 또는 `docs`.
2. 기술을 골라야 하면 [`docs/adr/TEMPLATE.md`](adr/TEMPLATE.md)를 복사해 **상태: 제안** ADR을 먼저 PR로 올립니다. 리뷰에서 합의되면 “채택”으로 바꿔 머지합니다.
3. 구현은 이번 실습과 같은 흐름입니다. 브랜치 → 커밋 → PR → 리뷰 1명 → 머지.
4. 트랙에서 정한 것은 이 문서 1절 표에 링크로 추가합니다.
