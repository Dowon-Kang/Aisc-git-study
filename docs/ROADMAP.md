# ROADMAP · 써 보고 찾은 문제에서 다음 기능으로

이번 실습 앱(일정·출석 보드)은 일부러 작게 만들었습니다. 그래서 **직접 써 보면 불편한 점이 바로 보입니다.** 이 문서는 그 불편을 출발점으로, 다음에 무엇을 만들 수 있는지와 누가 맡을 수 있는지를 정리합니다.

```text
① 써 보기 (1주) ──▶ ② 불편 기록 (Issue) ──▶ ③ 문제 고르기 (이 문서 1절) ──▶ ④ 손들기·짝 ──▶ ⑤ ADR 제안 PR ──▶ ⑥ 첫 기능 PR
```

튜토리얼은 없습니다. **어디를 바꾸면 되는지, 무엇을 먼저 정해야 하는지**만 적고, 기술 선택과 깊은 내용은 맡은 사람이 ADR과 PR로 채웁니다.

## 1. 써 보면 겪는 문제와 다음 기능

| # | 써 보면 겪는 장면 | 왜 그런가 (지금 구조) | 다음 기능 | 맡을 트랙 | 첫 Issue |
| --- | --- | --- | --- | --- | --- |
| P1 | 다음 스터디 시간을 정하려고 단톡방에서 서로 시간표를 묻고 또 묻는다 | 앱에 시간표·공강 정보가 없음 | 공강 찾기 (시간표 캡처 자동 인식) | 프론트 + AI (+ 백엔드) | [FREE-1](issues/roadmap/free-1-common-free-slots.md) → [FREE-2](issues/roadmap/free-2-timetable-capture.md) |
| P2 | 내 노트북에서 등록한 일정이 친구 폰에서는 안 보인다 | 저장이 브라우저 localStorage뿐 ([ADR-0001](adr/0001-localstorage-only.md)) | 서버 저장 | 백엔드 + DB | [BE-1](issues/roadmap/be-1-api-contract.md) → [DB-1](issues/roadmap/db-1-erd.md) |
| P3 | 스터디 현장에서 출석을 체크하려면 노트북을 열어야 한다 | 화면이 데스크톱 웹 하나뿐 | 출석 전용 모바일 화면 | 앱 (P2 이후) | [APP-1](issues/roadmap/app-1-attendance-only.md) |
| P4 | 앱 주소가 없어서 `npm run dev`를 켠 내 컴퓨터에서만 열린다 | 배포하지 않음 | 공개 주소 배포 | AWS | [OPS-1](issues/roadmap/ops-1-static-deploy.md) |
| P5 | 일정이 쌓이면 지난 회차에 누가 왔고 뭘 했는지 찾기 어렵다 | 한 화면에 목록만 있음 | 일정 상세 페이지 | 프론트 | [FE-1](issues/roadmap/fe-1-session-detail.md) |
| P6 | 회차마다 무엇을 배웠는지 정리하고 다음 주제를 정하는 게 귀찮다 | 주제가 한 줄 메모로만 남음 | 회차 요약·다음 주제 추천 | AI (서버 필요) | [AI-1](issues/roadmap/ai-1-session-summary.md) |

표에 없는 불편을 찾으면 그것이 P7입니다. ✨ 기능 폼으로 Issue를 만들고 “써 보면 겪는 장면”부터 적어 주세요.

## 2. 다음 단계: 써 보고, 고르고, 맡기

1. **써 보기 (실습 후 1주)** — 실제 스터디 일정과 출석을 이 앱으로 관리합니다. 불편할 때마다 Issue를 남깁니다. 고장은 🐛 버그 폼, 아쉬운 점은 ✨ 기능 폼.

   **누가 어떻게 쓰나**: 데이터가 브라우저마다 따로 저장되므로([ADR-0001](adr/0001-localstorage-only.md)) 실제 스터디 기록은 **운영 담당 한 명의 브라우저**로 합니다(주마다 돌아가며 맡아도 됩니다). 나머지는 각자 `npm run dev`로 띄워 일정을 넣고 출석을 체크해 보며 화면을 써 봅니다. 운영 담당이 넣은 일정이 내 화면에는 안 보이는 것 자체가 P2 문제를 겪어 보는 경험입니다. 불편은 그때그때 Issue로 남깁니다.
2. **고르기** — 1주 뒤 회고에서 1절 표와 새로 나온 Issue를 함께 보고, 다음에 풀 문제를 1~2개 정합니다. 기준은 “우리가 가장 자주 겪은 불편”입니다.
3. **손들기** — 맡고 싶은 사람은 해당 Issue에 아래처럼 댓글을 남깁니다. 한 사람은 한 번에 문제 하나만 주 담당으로 맡습니다.
   ```text
   맡을게요: @내아이디 · 짝: @짝아이디 · 해 보고 싶은 기술: (예: Express, PostgreSQL)
   ```
   관리자가 댓글을 보고 Assignees를 지정합니다.
4. **ADR 제안 (첫 PR)** — 코드보다 먼저 [`adr/TEMPLATE.md`](adr/TEMPLATE.md)로 “무엇을, 왜 이 기술로” 제안하는 PR을 올립니다. 리뷰에서 합의되면 상태를 “채택”으로 바꿔 머지합니다.
5. **첫 기능 PR** — 이번 실습과 같은 흐름입니다. 브랜치 → 커밋 → PR → 리뷰 1명 → 머지. 끝나면 1절 표의 해당 줄에 결과 링크를 추가합니다.

## 3. 순서와 의존 관계

```text
프론트(FE) ─────────────────────────────── 지금 바로 시작 가능
AI ──(1단계: 브라우저 밖 서버가 필요)──┐
백엔드(BE) ──▶ DB ──▶ AWS(서버 배포)   │
   │                                   │
   └──▶ 앱(APP)  ◀── 같은 API 사용 ─────┘
AWS(프론트 정적 배포) ──────────────────── 지금 바로 시작 가능
```

- **FE-1, OPS-1**은 지금 구조 그대로 시작할 수 있습니다.
- **DB·앱·서버 배포**는 백엔드의 API 계약(BE-1)이 머지된 뒤에 시작합니다.
- **AI**는 API 키를 브라우저에 둘 수 없으므로 서버가 필요합니다(4절 AI 참고).

## 5. 트랙별 안내 (문제를 맡았을 때 읽기)

### 백엔드 (BE)
- **출발점**: `storage.ts`의 `readSessions`·`saveSessions`. 지금은 동기 함수라서, 서버 호출로 바꾸면 비동기가 되고 `App.tsx`의 초기 로딩·저장 실패 처리가 달라집니다. 이 영향 범위를 ADR에 적습니다.
- **먼저 정할 것**: 경로와 메서드, 응답 형식(성공·오류를 한 모양으로 감쌀지), 오류 코드 목록, 인증 여부, 프론트 개발 서버 주소(`http://localhost:5173`) CORS 허용.
- **산출물**: `docs/API.md`(계약서) → 서버 코드는 저장소를 나눌지(ADR) 정한 뒤.
- **ADR 제목 예**: `0003-backend-framework.md`, `0004-api-response-format.md`

### DB
- **출발점**: `Session.attendees`가 이름 배열입니다. 관계형 DB라면 일정 테이블과 출석 테이블을 나누는 게 보통이고, 문서형 DB라면 지금 모양을 그대로 둘 수도 있습니다. 이 선택이 첫 ADR입니다.
- **먼저 정할 것**: DB 종류, 멤버를 테이블로 둘지(지금은 `members.ts` 상수), 삭제 시 출석 기록 처리, 로컬 개발용 DB 실행 방법.
- **산출물**: `docs/ERD.md`(그림 또는 표), 첫 스키마·마이그레이션.

### 프론트 (FE)
- **출발점**: 지금은 한 화면에 카드 네 개입니다. 일정이 많아지면 목록 → 상세 화면 분리가 필요합니다.
- **먼저 정할 것**: 화면(라우트) 목록과 주소 규칙, 상태를 어디에 둘지(지금처럼 App 상태 / 별도 상태 관리 도구), 새 패키지를 들일지.
- **지킬 것**: 새 화면도 `src/features/<기능>/` 폴더 규칙과 클래스 이름 규칙을 따릅니다.

### 앱 (APP)
- **출발점**: 같은 데이터를 쓰는 두 번째 클라이언트입니다. 서버가 없으면 웹과 데이터를 공유할 수 없으므로 BE-1이 먼저입니다.
- **먼저 정할 것**: 방식(웹을 설치형으로 만드는 PWA / 크로스플랫폼 앱 / 네이티브), 웹과 공유할 코드(`domain/types.ts`의 타입, 순수 함수), 앱 전용으로 둘 기능 범위.
- **추천 범위**: 처음에는 “출석 체크만” 되는 화면 하나.

### AI
- **출발점**: 일정의 `title`·`topic`과 출석 데이터. 예: 회차 주제 요약, 다음 스터디 주제 추천, 출석 패턴 알림 문구.
- **먼저 정할 것**: 무엇을 자동화할지(한 가지), 사용할 AI 서비스, 월 비용 상한, 보내는 데이터에 개인정보가 없는지, 결과가 틀렸을 때 화면에서 어떻게 보이게 할지.
- **꼭 지킬 것**: AI 서비스 API 키는 **브라우저 코드에 넣지 않습니다**. Vite에서 `VITE_`로 시작하는 환경변수는 빌드 결과에 들어가 누구나 볼 수 있습니다. 키는 서버에만 둡니다.

### AWS (OPS)
- **출발점**: 지금 앱은 `npm run build` 결과(`dist/`)만 올리면 되는 정적 사이트입니다. 서버가 생기면 서버 실행 환경과 DB가 추가됩니다.
- **먼저 정할 것**: 프론트·서버·DB를 각각 어디에 올릴지, 월 비용 상한과 예산 알림, 접속 키 보관(GitHub Secrets), 배포를 자동으로 할지(main push 시).
- **꼭 지킬 것**: 루트 계정 키를 만들지 않고 실습용 권한만 가진 사용자를 씁니다. 실습이 끝나면 만든 자원을 지웁니다.

## 6. P1 공강 찾기 자세히

각자 에브리타임 시간표를 **캡처해서 올리면** 바쁜 시간이 자동으로 인식되고, 모두가 비는 시간대를 계산해 보여 줍니다. 고른 시간대는 일정 등록으로 이어집니다. 프론트·AI·백엔드 트랙이 함께 쓰는 기능입니다.

```text
캡처 이미지 ──▶ 서버: 이미지 인식(AI) ──▶ 바쁜 시간 후보 JSON
                                             │
                     사용자가 그리드에서 확인·수정 ◀┘   ← 인식은 틀릴 수 있으므로 반드시 거침
                                             │
                     BusyBlock 저장 ──▶ findCommonFreeSlots ──▶ 공강 목록 ──▶ 일정 등록 폼 채우기
```

**순서: FREE-1 → FREE-2.** 계산과 확인 그리드(직접 칠하기)를 먼저 완성하면, 캡처 인식은 그 그리드를 “자동으로 미리 칠해 주는” 입력 방법이 됩니다. 인식이 실패해도 기능은 계속 쓸 수 있습니다.

| 정할 것 | 기본안 (ADR로 확정) |
| --- | --- |
| 데이터 모양 | `BusyBlock { member, day, start, end }` — `day`는 0(월)~6(일), 시간은 `HH:MM` 30분 단위. `Session`은 바꾸지 않음 |
| 계산 | `findCommonFreeSlots(blocks, members, { from: '09:00', to: '22:00', minMinutes: 60 })` 순수 함수 |
| 인식 결과 형식 | 정해진 JSON 스키마로만 받기(요일·시작·끝·확신도). 스키마에 안 맞으면 버리고 직접 입력 안내 |
| 개인정보 | 과목명·교수명·강의실은 저장하지 않고 **바쁜 시간대만**. 원본 이미지는 인식 후 서버에 남기지 않음 |
| 키·비용 | AI 키는 서버에만(브라우저·`VITE_` 금지), 월 비용 상한과 사용자당 하루 업로드 횟수 제한 |
| 정확도 확인 | 동의받은 샘플 캡처 5장 이상 + 정답 JSON을 두고, 칸 단위 일치율을 측정하는 스크립트로 모델·프롬프트를 비교 |
